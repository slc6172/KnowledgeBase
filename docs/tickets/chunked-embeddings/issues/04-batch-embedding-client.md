# 04 — 批次嵌入客戶端與實測驗證

**Type:** HITL

**Blocked by:** 03

**Status:** done(HITL 於 2026-10-03 完成)

**對應 User Story:** 1、4(見 `docs/specs/spec_chunked_embeddings.md`)

**What to build:** 在 `Embeddings.gs` 新增批次嵌入函式:全部段落放進**一個** `batchEmbedContents` 請求(每筆 `model` 與外層一致、`outputDimensionality: 768`);回傳向量數必須等於輸入數、每個向量 768 維,否則視為上游 AI 錯誤(整筆不寫入)。另附一個一次性的驗證函式(`tools/`,受 `REINDEX_ENABLED` 控管),由擁有者在 Apps Script 編輯器執行:用真實金鑰實測 (a) 回傳順序是否與請求一致(與單筆結果比對),(b) 一個請求最多可帶幾筆(40、41、100)。**人工步驟**:擁有者上傳驗證函式、執行、貼回日誌;若實測上限小於 40,批次大小常數需下修並分批送出。

**接縫:** GAS `httpFetch_`;人工執行(HITL)。

- [x] 請求形狀:一次請求、N 筆、每筆含 `model`、`content.parts[].text`、`outputDimensionality: 768`;金鑰放標頭,不在網址、不在日誌
- [x] 第 i 個回傳向量對應第 i 筆輸入(以不同向量的假回應驗證)
- [x] 向量數不符、任一向量維度不是 768、回應缺 `embeddings` → 丟出分類為 AI 的上游錯誤;錯誤訊息不含金鑰
- [x] 輸入為空陣列 → 不發出請求,回傳空陣列
- [x] 批次大小有單一常數;超過時自動分批送出,結果依序合併
- [x] 查詢向量的單筆函式行為不變
- [x] 驗證函式:未開啟 `REINDEX_ENABLED` 拒絕;只寫日誌;不回傳資料
- [x] **HITL**:擁有者貼回實測結果(順序、上限),結果記錄在票末的實作註記

> **實作註記:** (1) 批次客戶端在 `Embeddings.gs`:`requestEmbeddingBatch_`(單一請求,所有異常都轉成 AI 分類的上游錯誤)與 `generateEmbeddingsBatch_`(自動依 `EMBEDDING_BATCH_MAX_` 分批、依序合併、任一批失敗整個失敗)。官方文件確認:`batchEmbedContents` 每筆的 `model` 必須與外層一致,回傳依請求順序。
> (2) 驗證函式在 `tools/VerifyBatchEmbedding.gs`(`verifyBatchEmbedding`,受 `REINDEX_ENABLED` 控管,只寫日誌、只送短測試字串)。(3) **HITL 尚待完成**:擁有者上傳驗證函式、執行、把以「[驗證]」開頭的日誌貼回;若「最大成功筆數」小於 40,下修 `EMBEDDING_BATCH_MAX_`(客戶端已會自動分批,其他程式不用動)。
> (4) 因為這個結果最壞只會改一個常數,票 06 以後不等它就先做了;驗證結果會在票 10 上線前收進來。(5) 破壞驗證:客戶端五種、驗證函式四種,全部變紅。

> **第一次 HITL 的回饋(2026-10-03)**:擁有者執行時出現 `ReferenceError: requestEmbeddingBatch_ is not defined`(`VerifyBatchEmbedding.gs:69`)。**根因是我的設計錯誤**:驗證函式是要在新版程式上線「之前」執行,卻呼叫了只存在於新版 `src/Embeddings.gs` 的函式,而檔案說明還寫「需要專案目前已部署的版本」,說明與實作互相矛盾。測試沒抓到,是因為測試載入了新版的 `Embeddings.gs`——測試環境比真實環境多了東西。**修正**:驗證函式改為完全獨立(自己的 `verify*_` 函式與常數,只依賴舊版就有的 `getConfig_` 與 `httpFetch_`);測試改為**不載入**新版 `Embeddings.gs`,並加靜態檢查禁止引用任何新符號,以及『新舊並存不會名稱衝突』的測試;改回舊的寫法會讓 7 個測試變紅。同時檢查另一個工具:`Reindex.gs` 本來就依賴新版,已在檔案說明、README、上線清單寫明必須在 `clasp push` 之後才上傳。從錯誤訊息可知,前面三次單筆呼叫已成功,所以金鑰與開關都沒問題。

> **HITL 結果(2026-10-03,擁有者以真實金鑰執行獨立版驗證工具):** (1) **回傳順序一致**:批次第 1/2/3 筆與單筆第 1/2/3 筆的相似度,對角線都是 1.0000,其餘約 0.42(0.4169 ~ 0.4267)——官方文件說的「依請求順序」成立。(2) **40 筆、41 筆都成功**,所以 `EMBEDDING_BATCH_MAX_ = 40` 不需要調整,單次上限至少是 41。(3) **100 筆失敗,但那是 HTTP 429「超過目前額度」,不是筆數上限**:當時一分鐘內已經送了 3 + 3 + 40 + 41 = 87 筆,再送 100 筆就超過免費層每分鐘 100 個請求的額度(官方 rate limits 文件);這個結果只能用「批次裡每一段文字算一個請求」解釋(推論,文件未明載)。
> **衍生的修正**:原本的驗證工具把這個 429 一律記成「失敗」,而且沒有區分原因,日誌會讓人誤以為 100 是上限;已改為辨識 429、明說「不是筆數上限」,若 40 筆也遇到 429 則結論改為「無法判斷、等一分鐘重跑」,絕不建議下修。重建工具的 429 訊息也補上額度說明與「等一分鐘再執行 / 仍失敗可能是當天額度用完」。額度與實測結果已寫進 README、`docs/DESIGN.md` 決策 22 與 spec。
> **用量估算**:線上目前已發布 20 篇(含 4 篇 F03 測試文),約 45 段——重建只需要不到一分鐘額度的一半,一次執行就能完成。
