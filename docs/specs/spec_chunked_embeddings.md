# 分段向量與原子寫入 — Spec

**Triage label**:`needs-review`(擁有者確認後改為 `ready-for-agent`,再拆票)

**來源**:`/mycr` 第五輪(2026-10-02)F-02、F-03;F-03 的線上實測;`/grilling` 對談定案(2026-10-03,14 題)。

## Problem Statement

**1. 長文的後半段對搜尋、相關文章、AI 問答的檢索而言根本不存在。** 目前每篇文章只存一個向量,而嵌入模型
(`gemini-embedding-001`)單筆輸入上限是 2,048 token,超過的部分被**靜默截斷**,沒有任何錯誤或提示。
2026-10-02 在線上環境實測(兩個互不相干的主題「烹飪」「天文」,兩個順序各一篇約 14,900 字長文,另有兩篇
純主題短文當對照):長文發布成功、沒有報錯;「烹飪→天文」那篇離純烹飪對照 0.046、離純天文對照 0.364,
「天文→烹飪」那篇反過來(0.039 / 0.362);而純烹飪與純天文本來就相距 0.351。也就是長文後半段對向量的貢獻是零。
擁有者目前 17 篇文章中只有 1 篇超過 4,000 字,影響還小;但文章一旦變長,使用者寫了內容卻永遠搜不到,而且毫無徵兆。

**2. 文章的標籤同步不是原子的。** 更新標籤是「先刪光舊的關聯、再插入新的」兩個獨立請求,中間失敗會讓
**內容已更新、標籤全部消失**。改走 Edge Function 代理後多了一跳與冷啟動,瞬斷機率比直連時高。標籤合併
(`mergeTags_`)是逐篇文章的多步驟流程,同樣可能半途停住。

**3. 一旦向量改成多段,「內容與向量一起提交」的保證會消失。** 目前向量是 `articles` 的一個欄位,和內容合併在
同一個 PATCH 裡,所以是原子的(`spec_article_write_consistency`)。向量搬到獨立資料表後,如果不重新設計,會出現
「內容是新的、段落向量還是舊的」——正是當初修掉的部分提交問題。

**4. 資料庫函式與擴充功能的衛生問題。** 四個函式沒有固定 `search_path`,`vector`、`pg_trgm` 兩個擴充功能裝在
`public`(Supabase 安全顧問 Lint 0011、0014)。線上目前只有測試資料,現在整理的成本最低。

## Solution

每篇已發布文章被切成多段(每段最多約 1,500 字),**每段各有一個向量**,存在新的資料表 `article_chunks`。搜尋與
相關文章改用「該文章最接近的那一段」的距離,因此文章任何位置的內容都找得到。

文章、段落、標籤的寫入全部收進**一個資料庫函式(RPC)`save_article`**,在單一交易裡完成,任何一步失敗就整筆不生效。
標籤合併同樣收進 `merge_tags`。GAS 不再直接讀寫 `article_chunks`,代理的資料表白名單維持 6 張,只新增兩個 RPC。

`articles.embedding` 欄位與它的索引移除。所有資料庫函式一律固定 `search_path`,`vector`、`pg_trgm` 搬到
`extensions` schema。既有文章的段落向量由一個**獨立、一次性的重建工具檔**產生(不在 `src/` 內,有三道防護,
可中斷續跑),換嵌入模型時同一個工具可以再用一次。資料庫行為的測試新增一種接縫:對真實 PostgreSQL(含 pgvector)
執行的整合測試,CI 用服務容器真的跑。

**已查證的外部事實(2026-10-03):**
- Gemini 官方 API 文件:`gemini-embedding-001` 單筆輸入上限 2,048 token;`models.batchEmbedContents`
  一個請求可帶多筆,每筆的 `model` 必須與外層一致,回傳的 `embeddings[]` **依請求的相同順序**排列。
- Supabase 官方文件:Lint 0014 的修法就是 `alter extension <名稱> set schema <schema>`;官方範例函式使用
  `set search_path = ''` 搭配全限定名稱(本專案選擇較簡潔的固定 `public, extensions`,見〈Implementation Decisions〉)。

## User Stories

**擁有者(寫文章)**
1. 作為擁有者,我發布一篇 15,000 字的長文後,用文章最後一節的內容搜尋也要能找到它,這樣我不必擔心「寫了卻搜不到」。
2. 作為擁有者,我發布的文章若長到超過 40 段(約 6 萬字),我要收到明確說明(段數與上限、建議拆成多篇),而不是被悄悄截斷。草稿不受這個限制。
3. 作為擁有者,我儲存文章時,內容、標籤、搜尋用的向量要「一起生效或一起不生效」,不會出現內容是新的、標籤卻全部消失。
4. 作為擁有者,Gemini 失敗時我儲存或發布的文章要整筆不生效(與現在一致),並看到安全的錯誤訊息。
5. 作為擁有者,我取消發布再重新發布時,系統重新計算全部段落,確保搜尋用的向量和最新內容一致。
6. 作為擁有者,合併兩個標籤時,不會因為中途失敗留下一半搬完的狀態。

**搜尋與相關文章的使用者**
7. 作為搜尋者,查詢任何出現在文章任何位置的主題,只要語意夠接近就要找得到那篇文章。
8. 作為搜尋者,搜尋結果的排序與篩選(分類、標籤、僅已發布)行為不變。
9. 作為讀者,文章詳情下方的「相關文章」要能依文章任一段的內容找出相近的文章,且不推薦草稿與自己。
10. 作為 AI 問答的使用者,被檢索到的文章仍以整篇全文送給 Gemini(行為與現在一致),答案品質不因這次改版而變動。
11. 作為搜尋者,語意搜尋失敗時的降級行為(只用關鍵字、顯示提示)完全不變。

**擁有者(維運)**
12. 作為擁有者,我要一個一次性的工具,能替所有已發布文章重新計算段落向量,並且 6 分鐘執行時限到了可以接著跑,不會重複花費。
13. 作為擁有者,這個工具在我沒有明確啟用時不能被任何人觸發;就算我上傳後忘了刪除,跑完也要自動失效。
14. 作為擁有者,我要能先用「試跑」看到文章數、段數與預估的 Gemini 請求數,確認無誤才正式執行。
15. 作為擁有者,將來換嵌入模型時,我只要改一個常數,就能用同一套流程重算;模型不同的段落會被視為待重建。
16. 作為擁有者,我要一份逐步清單說明上線順序,因為資料庫與程式必須一起換,中間有短暫停機。

**維護者**
17. 作為維護者,我要六個資料庫函式都固定 `search_path`、擴充功能不在 `public`,讓安全顧問的相關警告消失。
18. 作為維護者,搜尋排序、最近段落、原子寫入、段數上限、合併標籤這些放進 SQL 的行為,要有會在 CI 變紅的測試。
19. 作為維護者,`docs/schema.sql` 永遠是從無到有的最終狀態,不含升級痕跡。
20. 作為維護者,代理的白名單測試要明確區分「刻意不對外開放的表」與「忘記加入白名單的表」。

## Implementation Decisions

**資料模型**
- 新資料表 `article_chunks`:每段一列,欄位為所屬文章(文章刪除時連帶刪除)、段落序號(從 0 起,同一篇內唯一)、
  **段落文字**、向量(768 維,cosine)、`embedding_model`(例如 `gemini-embedding-001/768`)、建立時間。
- 存**段落文字**而不是在 `content_md` 裡的起訖位置:JavaScript 與 PostgreSQL 計算字元位置的方式不同(代理對、
  表情符號會對不齊),存位置會悄悄切錯段落;段落與文章在同一個交易裡更新,不會不一致。
- 向量欄位建 HNSW 索引(cosine)。資料表開啟 RLS 且不建 policy(與其他表一致)。
- `articles.embedding` 欄位與它的索引**直接移除**(專案以從無到有佈建為前提,不保留相容欄位)。
- `article_chunks` **不加入代理的資料表白名單**:所有讀寫都經 RPC,GAS 不需要直接存取。

**切段規則(在 GAS 端執行,純函式)**
- 每段最多約 1,500 字(以 JavaScript 字串長度計),不重疊。即使最壞情況 1 字 1 token 也低於 2,048 的上限,不需要實測。
- 優先在段落邊界(空行)切;單一段落仍過長時依序退而求其次:換行、句末標點(。!?.!?)、最後才是硬切。
  硬切不可切斷代理對(surrogate pair)。
- 文章內容在 1,500 字以內 → 只有 1 段(與現在的行為等價)。內容為空 → 仍產生 1 段(空文字),讓文章至少能以標題被找到。
- **送去嵌入的文字**是「標題 + 空行 + 該段文字」,讓每段的向量帶著主題脈絡;**資料庫存的段落文字**只含該段本身。
- 段數上限 40。超過時**拒絕發布**,在呼叫 Gemini 之前就檢查,回傳明確且安全的訊息(含實際段數與上限);
  草稿的儲存不受影響(草稿不產生段落)。

**嵌入呼叫**
- 發布 / 更新已發布文章時,把全部段落放進**一個** `batchEmbedContents` 請求(模型、`outputDimensionality: 768` 與現行單筆呼叫一致)。
- 回應的向量數必須等於段數、每個向量必須是 768 維,否則整筆視為上游 AI 錯誤、不寫入任何東西(與現在的一致性原則相同)。
- 官方文件保證回傳順序與請求一致;仍以測試鎖住「第 i 個向量對應第 i 段」。查詢向量維持單筆 `embedContent`,不變。
- 重試與退避不在本次範圍。

**`save_article` RPC(原子寫入)**
- 一個函式,單一交易,涵蓋「建立 / 更新文章欄位、狀態、全部段落、標籤集合」。呼叫端傳入:文章 ID(空值代表建立)、
  文章欄位(可選)、狀態、標籤 ID 清單(可選)、段落清單(可選,每段含文字與向量)、`embedding_model`。
- 語意:各部分彼此獨立可選——
  - 欄位未提供 → 文章欄位不變;標籤清單未提供 → 標籤不變,提供(含空清單)→ 標籤集合整組換成該清單(在交易內以差集完成);
  - 段落清單未提供 → 段落不變,提供 → **整批取代**該文章的全部段落。
- 對應現有流程:建立草稿(欄位 + 標籤,無段落);更新草稿(欄位 + 標籤);更新已發布文章(欄位 + 標籤 + 段落);
  發布(狀態 + 段落);**取消發布(只改狀態,段落保留,不碰)**——搜尋與相關文章本來就只看已發布,保留不會被搜到,
  重新發布時整批重算覆蓋;重建工具(**只有段落**)。
- 函式內驗證:狀態值合法、段落數 ≤ 40、段落序號連續;違反任何一項整筆回滾。
- 標籤本身的「找或建」(`findOrCreateTag_`)仍在 RPC 之前由 GAS 執行;萬一之後 RPC 失敗,殘留的是一個無人引用的標籤,無害。
- 回傳儲存後的文章(GAS 沿用現有的正規化)。加入代理的 RPC 白名單。
- 取代:`syncArticleTags_`、`createArticle_` / `updateArticle_` / `setArticleStatus_` 內各自的 PATCH + 向量 + 標籤多步驟呼叫。
  刪除文章維持現狀(連帶刪除段落由資料庫的 cascade 完成)。批次改分類、批次加標籤維持現狀(逐篇獨立、結果分開回報)。

**`merge_tags` RPC**
- 單一交易:來源與目標標籤相同或不存在 → 拒絕;同時擁有兩者的文章只刪除指向來源的關聯,其餘文章的關聯改指向目標,最後刪除來源標籤。
- 取代 `mergeTags_` 的逐篇多步驟流程。加入代理的 RPC 白名單。

**檢索函式**
- `hybrid_search_articles`:語意那一路改為「每篇文章取其最接近的那一段」的 cosine 距離,門檻語意不變(預設 0.4);
  關鍵字那一路**維持原樣**(對整篇標題 + 內文做 trigram 相似度);融合排序、篩選(分類、標籤、僅已發布)、降級(查詢向量為空時語意那一路自然為空)不變。
- 回傳形狀:除文章 ID 與順序外,**額外回傳命中的段落序號與段落文字**(僅由語意那一路命中時才有值),作為 F-14(AI 問答只送命中段落)的資料來源。
  本次 GAS **不使用**這兩個欄位(GAS 目前只取 ID 再重新查詢整列),只由 SQL 測試覆蓋。函式簽名/回傳型別改變,新舊不並存。
- `related_articles`:來源文章的每一段分別找最近鄰,取每篇候選文章的最小距離;門檻維持 0.6;排除自己與草稿;最多 3 篇不變。
- `articles_by_tags`、`touch_updated_at`:邏輯不變,僅補上 `search_path`。
- 門檻 0.4 / 0.6 原本是用整篇向量校準的;段落向量的距離分布可能不同。**先沿用**,實作完成後用真實資料與 F03 測試文章量測,再決定是否調整。

**資料庫衛生**
- 七個函式(`touch_updated_at`、`hybrid_search_articles`、`related_articles`、`articles_by_tags`、`save_article`、`merge_tags`、`articles_needing_reindex`)
  一律 `set search_path = public, extensions`。取捨:官方範例用空的 `search_path` 加全限定名稱,安全性略高但每個運算子都要寫成
  `operator(extensions.<=>)`、容易寫錯;單人專案且 `public` 不開放建立物件,選擇較簡潔的固定值。
- `schema.sql` 開頭建立 `extensions` schema 並把 `vector`、`pg_trgm` 建在其中;型別與運算子類別用全限定名稱
  (`extensions.vector(768)`、`extensions.vector_cosine_ops`、`extensions.gin_trgm_ops`),不依賴使用者的 `search_path`。

**重建工具(`tools/` 內的獨立檔案)**
- 放在專案根目錄的 `tools/`,**不在 `src/`**:clasp 的 `rootDir` 是 `./src`,一般推送不會帶上它;需要時手動上傳到 Apps Script 專案,用完刪除。
- 入口函式**不加底線**(才看得到、能在編輯器手動執行):`reindexAllArticles`(正式)、`reindexDryRun`(試跑)。
- 防護:(1) Script Property `REINDEX_ENABLED` 必須為 `true`,否則直接拒絕(**試跑也一樣**,保持「沒開關就什麼都不做」一條規則);(2) **全部處理完後自動刪除這個 Property**
  (即使忘了刪檔案,工具也已失效);(3) 試跑只寫日誌(文章數、段數、預估請求數),不呼叫 Gemini、不寫入、不回傳資料。
  任何入口都不回傳文章內容(避免上傳後被公開呼叫時外洩)。
- 處理範圍:已發布且「沒有任何段落,或有段落的 `embedding_model` 與目前常數不同」的文章。草稿略過。超過 40 段的文章記錄在日誌並略過,不讓整批失敗。
- 時限:單次執行 6 分鐘上限,約 5 分鐘時存檔停止並記錄進度(已處理 / 剩餘),Property 保留;再按一次接續。遇到 429 同樣優雅停止。
- 寫入走同一個 `save_article`(只帶段落),不另開寫入路徑。
- 向量維度寫在欄位型別上;換成**不同維度**的模型需要改 schema,工具處理不了(文件需寫明)。

**代理**
- `ALLOWED_RPCS` 新增 `save_article`、`merge_tags`、`articles_needing_reindex`;`ALLOWED_TABLES` 維持 6 張。**必須重新部署 Edge Function。**
- `articles_needing_reindex(模型)`:唯讀輔助 RPC,回傳「已發布且沒有任何段落、或有段落的 `embedding_model` 與傳入值不同」的文章 ID。
  需要它是因為 `article_chunks` 不對 GAS 開放,重建工具無法直接判斷哪些文章待重建(擬票時發現,2026-10-03 補入 spec)。
- 既有的「白名單 = schema 全部資料表」測試改為明確列出「刻意不對外開放的資料表」(僅 `article_chunks`),並要求其餘資料表一律在白名單內。

**上線(Q11:不做相容層,接受短暫停機)**
- 順序:(1) 在真實 PostgreSQL 驗證 migration → (2) 套用到線上(建立 `extensions` schema、搬移擴充功能、建立 `article_chunks`、
  新函式、丟棄舊函式簽名與 `articles.embedding`)→ (3) 部署代理 → (4) `clasp push` 並發新版 Web App →
  (5) 上傳重建工具,設 Property,試跑,正式執行 → (6) 刪除工具檔。
- 步驟 (2) 到 (4) 之間,舊版網站的發布、編輯、搜尋會報錯;線上只有測試資料、只有擁有者使用,接受。
- 線上舊向量無法轉換成段落,一律靠重建工具重算。

**文件與使用者訊息**
- 超過段數上限的訊息:說明這篇文章切成 N 段、上限 40 段,建議拆成多篇或縮短內容;文字為安全訊息,不含內部細節。
- 需更新:`docs/schema.sql`、`docs/DESIGN.md`(原決策「整篇一個向量、不切 chunk」被取代,資料流與架構圖同步)、
  README(快速開始、變更紀錄)、`CLAUDE.md`(新增 SQL 整合測試接縫、`tools/` 資料夾、`extensions` schema)。

## Testing Decisions

**好測試的標準**:只驗證外部可觀察的行為(搜尋找不找得到、寫入有沒有生效、拒絕時有沒有動到資料),不鎖內部實作。

**接縫(已與擁有者確認)**
1. **新增:SQL 整合測試**,對真實 PostgreSQL 16 + pgvector 執行專案的 `docs/schema.sql`。以環境變數 `TEST_DATABASE_URL`
   啟用,未設定時自動跳過(本機 `npm test` 不需要資料庫);CI 以 `pgvector/pgvector:pg16` 服務容器真的跑。
   需新增開發相依 `pg`(照例以 `npm audit` 把關)。向量用手工構造的 768 維向量(沿座標軸的單位向量),距離可精確預期,**不呼叫 Gemini**。
2. GAS 的 `httpFetch_`(切段、批次嵌入呼叫、寫入流程送出的請求、重建工具)。
3. Deno 的 `handleRequest`(代理白名單)。
4. 靜態文字掃描(`schema.sql` 與設計文件的最終狀態)沿用既有的 `SchemaGreenfield` 測試並更新。

**SQL 整合測試要涵蓋**
- 在全新資料庫上載入 `schema.sql` 成功;`vector`、`pg_trgm` 位於 `extensions`;`public` 中沒有它們的物件。
- 七個函式的設定都含固定 `search_path`;七張資料表都開啟 RLS;匿名角色讀不到任何資料表,包括 `article_chunks`。
- 搜尋:長文**最後一段**的內容可被找到(以最接近段落排序);語意門檻;僅已發布;分類與標籤篩選;關鍵字那一路與融合排序不變;
  查詢向量為空時只剩關鍵字結果;命中段落的序號與文字正確(只由關鍵字命中時為空)。
- 相關文章:任一段相近即命中;不含自己與草稿;最多 3 篇;門檻 0.6。
- `save_article`:建立草稿(含標籤)、更新、發布(帶段落)、取消發布(段落保留)、只重建段落、標籤整組取代(差集,不經過「全刪再插入」的空窗)。
  **原子性**:刻意讓其中一步失敗(例如非法狀態、段數 41、向量維度錯誤)→ 文章欄位、段落、標籤三者都維持原狀。
- 段數上限剛好 40 通過、41 拒絕;段落序號不連續被拒絕。
- `merge_tags`:一般搬移;同時擁有兩個標籤的文章;來源等於目標、標籤不存在被拒絕;失敗時整筆回滾。
- 刪除文章連帶刪除段落(cascade)。
- 以校準資料重現 F-03 的情境:前半段與後半段主題不同的長文,後半主題的查詢能找到它。

**GAS 測試要涵蓋**
- 切段:各邊界規則(段落、換行、句末標點、硬切)、不重疊、不切斷代理對、1,500 字以內為單段、空內容為單段、超過 40 段回報、
  嵌入文字含標題而儲存文字不含。
- 批次嵌入:請求形狀(一次請求、每筆模型一致、維度 768)、第 i 個向量對應第 i 段、向量數或維度不符 → 上游 AI 錯誤、錯誤訊息不含金鑰。
- 寫入流程:建立、更新、發布、取消發布各自只送出**一個** `save_article` 請求且內容正確;超過段數上限時**不呼叫 Gemini**也不呼叫 `save_article`;
  Gemini 失敗時不呼叫 `save_article`;`syncArticleTags_` 不再存在。
- 搜尋、相關文章、AI 問答對新的 RPC 回傳形狀仍能運作,降級行為不變。
- 重建工具:未設 Property 一律拒絕(含試跑);試跑不呼叫 Gemini 也不寫入;處理範圍判斷(無段落、模型不同、草稿、超過 40 段);6 分鐘時限前停止並可續跑;
  全部完成後刪除 Property;入口函式不回傳文章內容;工具檔不在 `src/` 內。
- 既有的「公開函式必須在 PUBLIC_ALLOWLIST」掃描只涵蓋 `src/`;另以測試確認 `tools/` 不會被 clasp 推送(`rootDir` 為 `./src`)。

**Deno 測試**:`ALLOWED_RPCS` 包含新增的三個 RPC;`article_chunks` 不在資料表白名單;對 `article_chunks` 的直接請求回 403。

**既有測試的處理**:`EdgeFunctionProxyConfig` 的白名單一致性測試依上述改寫;`SchemaGreenfield`、`NoServiceRoleInGas` 等依新 schema 更新;
其餘不應需要修改斷言。

**Prior art**:`test/Articles.test.js`(寫入流程的 `httpFetch_` 測法)、`test/Search.test.js`、`supabase/functions/kb-proxy/handler_test.ts`、
`test/SchemaGreenfield.test.js`;SQL 行為過去只在開發時於沙箱手動驗證(見 `spec_search_degradation` 的已驗證事實),這次改為會紅的自動測試。

## Out of Scope

- **AI 問答只送命中段落(F-14)**:本次 RPC 只把命中段落備好,GAS 不使用,AI 問答仍送整篇;送幾段、要不要補上下文、對回答品質的影響,另走自己的 `/grilling`(後來由 `spec_rag_excerpts.md` 處理:送命中段落的節錄,不補上下文)。
- **關鍵字那一路改為段落層級**:現在拿整篇文章做 trigram 比對,長文幾乎達不到門檻,本來就偏弱。要改需要另建段落層級的 trigram 索引,範圍再大一塊;列為已知限制。
- **重新校準 0.4 / 0.6 門檻**:先沿用,實作完成後量測再決定。
- **Gemini 呼叫的重試與退避**、`taskType` / `title` 等嵌入最佳化參數(官方文件說 `RETRIEVAL_DOCUMENT` 搭配 `title` 可提升檢索品質,但這會改變向量空間,需與查詢端一起評估)。
- **更新已發布文章時,標題與內文沒變就跳過重算**:本次維持「更新已發布文章一律重算」,與現況一致。
- **非同步批次嵌入 API**(`asyncBatchEmbedContent`)與 `halfvec`:本專案規模不需要。
- **前端畫面**:沒有任何前端變動(搜尋結果不顯示命中段落)。
- **相容層 / 升級腳本**:不做,見〈上線〉。
- 批次改分類、批次加標籤:維持逐篇獨立、分開回報的現狀。

## Further Notes

- **關閉的審查項目**:mycr 第五輪 F-02、F-03。F-14 與 F-08(AI 問答成本、重複嵌入)已由 `spec_rag_excerpts.md` 處理。
- **為什麼不選「分段後取平均、仍是一個向量」**:實作較小(不改 schema),但多主題長文會被稀釋、可能掉出 0.4 門檻,且無法知道命中哪一段;
  擁有者選擇分段表,因為線上只有測試資料,現在改 schema 成本最低,而且它同時是 F-14 的基礎。
- **待實作時驗證的事實**:(1) `batchEmbedContents` 單次請求的筆數上限與回傳順序——**已於 2026-10-03 以真實金鑰實測**:順序一致(批次第 i 筆與單筆第 i 筆的相似度為 1.0000)、
  40 筆與 41 筆都能放進同一個請求;100 筆回 HTTP 429 是**額度**錯誤(免費層每分鐘 100 個請求,前面已用掉 87 筆),不是筆數上限——本專案上限 40 段維持不變。
  官方沒寫批次裡每筆算不算一個請求,但實測只能用「每一段文字算一個」解釋(推論)。對成本與重建的影響見 DESIGN.md 決策 22;(2) `alter extension … set schema` 對 `vector`、`pg_trgm` 的可行性,
  先在本機 PostgreSQL 16 驗證,再套用到線上;(3) PostgREST 對 `extensions.vector` 型別參數的轉換,套用 migration 後用應用程式實際搜尋一次確認。
- **向量距離與正規化**:距離運算子用 cosine,縮減維度後向量未正規化也不影響結果,不需額外處理。
- **成本**:發布一篇 N 段的文章是一個批次請求,token 用量約為全文字數;更新已發布文章每次都重算(同現況)。重建工具對每篇已發布文章一個請求,
  注意免費額度。
- **風險**:(1) 搜尋函式簽名與回傳型別變更,GAS 與資料庫必須同時換(已有上線順序);(2) 重建工具若上傳後忘了刪除又發了新版 Web App,
  會成為公開入口——所以有 Property 開關與自動解除,且不回傳任何內容;(3) 社群文章曾提到批次 API 的回傳順序問題,與官方文件相反,
  以測試與實測把關;即使真的錯位,因為檢索是以文章為單位取最小距離,只會影響「命中段落文字」的對應,不會讓文章找不到。
- **後續工作**:F-14(AI 問答只送命中段落)已由 `spec_rag_excerpts.md` 處理;段落層級的關鍵字比對、門檻校準、Gemini 重試皆可獨立排程。
