# Spec：錯誤訊息對外揭露範圍收斂

**Triage label**：`ready-for-agent`

**來源**：`mycr-report-2026-09-18.md`(五層程式碼審查報告)Finding 1、Finding 2，經 grilling 對談
逐項定案。

## Problem Statement

這個知識庫工具的讀取功能刻意設計成任何人不需登入、不需密碼就能直接呼叫。目前當底層呼叫 Supabase
資料庫、Supabase Storage 或 Gemini API 失敗時，這幾個模組會把對方回應的原始內容（HTTP 狀態碼、
完整錯誤文字）直接包進例外訊息裡往外拋；前端唯一的錯誤顯示機制又會把收到的例外訊息原樣顯示給
使用者。兩件事合起來，代表任何匿名訪客光是讓搜尋、瀏覽這類完全不需要密碼的功能出錯，就能看到資料庫
或 AI 服務的內部錯誤細節——這些細節可能透露欄位名稱、約束名稱、查詢結構等實作資訊，對一個完全
未認證的訪客而言沒有揭露的必要，也可能被用來當作進一步攻擊的偵察素材。持有寫入密碼、能呼叫問答
功能的人，一樣會在對應的失敗情境看到同等級的原始細節。

除此之外，呼叫 Gemini 產生向量嵌入或產生問答內容的兩個地方，目前只檢查了 HTTP 狀態碼，沒檢查
成功回應（2xx）本身的欄位是否存在。Gemini 在內容被安全過濾機制擋下時可能回傳缺少預期欄位的
回應，導致程式在讀取欄位時直接丟出看不懂的型別錯誤，而不是一句能理解的訊息。

## Solution

把「使用者最終會看到什麼」跟「系統內部記錄了什麼」分開：所有直接呼叫 Supabase 資料庫、Supabase
Storage、Gemini API 而失敗的地方，繼續在系統內部（執行紀錄）保留完整的原始錯誤內容，但最終往外
（回到呼叫端、最後顯示給使用者）拋出的訊息，一律換成一句按錯誤來源分類、不含任何內部細節的通用
訊息。這個轉換集中在少數幾個對外進入點上處理，不需要逐一修改每個會呼叫外部服務的函式；密碼驗證
錯誤、欄位驗證訊息、流量限制訊息這類原本就已經是安全、看得懂內容的既有錯誤，不受影響，維持原樣
直接顯示。

另外，Gemini 呼叫在讀取回應欄位前先確認欄位存在，欄位不存在時直接給出一句本身就安全、看得懂的
訊息，取代目前會發生的型別錯誤。

## User Stories

1. 身為任何瀏覽這個知識庫的匿名訪客，我希望搜尋或瀏覽文章時如果剛好碰到後端服務出問題，看到的是
   一句看得懂的提示，而不是資料庫或 AI 服務的內部錯誤細節。
2. 身為知識庫擁有者，我希望即使對外顯示的訊息變成通用提示，自己事後還是能在 Apps Script 執行紀錄
   裡查到完整的原始錯誤內容（狀態碼、回應內容），方便診斷問題。
3. 身為知識庫擁有者，我希望在執行紀錄裡看到錯誤時，能看出是哪個操作（搜尋、建立文章、上傳附件等）
   觸發的，不用光憑一段錯誤文字自己猜。
4. 身為使用密碼保護功能新增/修改/刪除文章的人，我希望這些寫入操作碰到後端服務失敗時，看到的也是
   通用提示，不會因為我持有密碼就被多顯示一些不必要的內部細節。
5. 身為使用 AI 問答功能的人（需要密碼），我希望問答過程中如果 Gemini 服務本身出問題，看到的是
   通用提示，不是原始的 API 錯誤內容。
6. 身為使用者，我希望「資料庫/檔案儲存出問題」跟「AI 服務出問題」這兩種情境顯示的訊息不同，這樣
   我至少能判斷是搜尋/存檔壞了，還是問 AI 這件事本身壞了，而不是完全分不出來。
7. 身為使用者，我希望在語意搜尋或 AI 問答時，如果 Gemini 因為內容被安全機制擋下、或回應格式跟
   預期不同，看到的是一句清楚的提示，不是程式當掉般看不懂的錯誤。
8. 身為知識庫擁有者，我希望「這個部署忘了設定 Gemini API 金鑰」這類部署設定問題，維持現在會清楚
   顯示的樣子，不要被這次修正一併蓋成通用訊息，因為這句話本來就是為了幫我自己診斷部署問題而存在
   的，內容也不含任何 Supabase/Gemini 的回應細節。
9. 身為維護者，我希望這次修正不會影響到目前已經在驗證「底層函式有沒有正確把狀態碼跟回應內容往上
   傳」這件事的既有測試，這些測試原本要驗證的行為本身沒有錯，不該被這次資安修正牽連著改寫。
10. 身為維護者，我希望以後新增一個新的公開讀取函式或寫入操作時，套用這個保護機制的方式是輕量、
    一致、容易照抄的，不需要每次都重新設計一次。
11. 身為維護者，我希望能在專案既有的「已知問題修復紀錄」裡查到這批問題的根因與修法，不用重新
    踩一次同樣的坑。

## Implementation Decisions

- **新增一個共用的錯誤轉換機制**：獨立成一個新模組，提供一個包裝函式，接受一個操作標籤字串跟一段
  要執行的邏輯。執行過程中如果抓到一個被標記為「上游服務錯誤」的例外，就把完整原始內容（含操作
  標籤）寫進執行紀錄，然後另外拋出一句依錯誤分類挑選的通用訊息；抓到的例外如果沒有這個標記，原封
  不動往外拋，不做任何轉換。
- **標記上游服務錯誤**：SupabaseClient、StorageClient、Embeddings、RagChat 四個模組裡，實際呼叫
  外部服務、依 HTTP 狀態碼判斷失敗的那四個拋出點，改成在建構例外物件時額外標記為「上游服務錯誤」。
  例外訊息本身的內容不變——這四個模組既有測試裡對「例外訊息包含原始狀態碼跟回應內容」的斷言，
  預期不受影響。
- **通用訊息分兩類**：牽涉 Supabase 資料庫或 Supabase Storage 的上游服務錯誤，統一轉換成同一句
  「資料服務暫時發生問題，請稍後再試」類的訊息；牽涉 Gemini（embedding 或問答）的上游服務錯誤，
  統一轉換成同一句「AI 服務暫時發生問題，請稍後再試」類的訊息。
- **設定類錯誤不受影響**：Embeddings、RagChat 模組裡各自「缺少 Gemini API 金鑰設定」的檢查，維持
  現狀，不標記、不轉換，因為這類錯誤發生在真正呼叫 Gemini 之前，性質上是部署設定問題（跟既有的
  「缺少寫入密碼設定」錯誤同一類），不含任何上游服務回應內容。
- **套用範圍——密碼保護的寫入路徑**：所有密碼保護的寫入操作目前都收斂在 Auth 模組唯一的一個分派
  入口，只需要在這一個入口套用一次轉換包裝，即可涵蓋全部寫入操作，不需要逐一修改每個寫入函式。
- **套用範圍——公開讀取路徑與問答功能**：沒有共用分派入口、各自獨立對外暴露的公開讀取函式（列於
  Auth 模組現有白名單註解裡的全部項目），以及獨立於白名單之外、自行驗證密碼的問答功能，各自在
  自己的函式主體套用同一個轉換包裝，操作標籤直接用該函式對外可見的名稱，方便執行紀錄事後依名稱
  追查。
- **Gemini 回應格式檢查**：讀取 embedding 數值、問答候選內容這兩處欄位之前，先確認欄位是否存在；
  不存在時直接拋出一句已經是對外安全內容的清楚訊息（不含任何原始回應內容），不標記為上游服務
  錯誤，也不經過轉換包裝——因為這句訊息本身已經足夠安全，多一層轉換沒有額外價值。
- **前端不需改動**：前端目前的錯誤顯示機制只是原樣顯示收到的例外訊息內容，不需要因為這次修正
  調整顯示邏輯本身。

## Testing Decisions

- 好的測試只驗證外部可觀察的行為：呼叫入口最終收到的錯誤訊息內容，以及（透過測試替身）原始詳細
  內容有沒有真的被寫進執行紀錄——不綁定「用了哪個內部標記屬性」這種實作細節。
- 新增的轉換包裝函式本身需要獨立測試：標記為上游服務錯誤的例外，驗證抓到後正確轉換成對應分類的
  通用訊息；沒有標記的例外，驗證原封不動往外拋；測試替身驗證記錄動作被呼叫時帶有預期的操作標籤
  跟原始內容。
- SupabaseClient、StorageClient、Embeddings 三份既有測試檔涵蓋的「底層函式直接拋出詳細錯誤內容」
  行為，這次修正不改變，這些既有測試預期維持全部通過、不需要修改斷言內容。
- 每個套用轉換包裝的進入點（密碼保護的分派入口、全部公開讀取函式、問答功能），都需要補至少一個
  測試案例：模擬底層丟出標記為上游服務錯誤的例外，驗證該進入點最終往外丟的是對應分類的通用訊息，
  不是原始內容。
- Gemini 回應格式檢查新增的兩個分支（缺 embedding 數值、缺問答候選內容），各補一個測試案例：模擬
  一個格式正常的 2xx 回應但缺少預期欄位，驗證丟出的是清楚訊息，不是原生的型別錯誤。
- 前端測試延續專案現有的靜態文字掃描慣例；這次修正不影響前端程式碼本身，不需要新增前端測試。

## Out of Scope

- 前端顯示邏輯本身的改動——它只是原樣顯示後端傳來的訊息，這次修正只改變後端傳出的訊息內容。
- 密碼保護的寫入路徑跟公開讀取路徑之間，讓密碼持有者看到比匿名訪客更詳細的錯誤內容——對談中已
  確認兩者採用同一套通用訊息，不分等級。
- 改變任何判斷錯誤發生與否的既有邏輯（例如 HTTP 狀態碼門檻、RAG 對話紀錄長度限制），這次修正
  純粹只改變「錯誤內容最終要不要完整暴露給呼叫端」。
- Finding 3（`batchAddTagsToArticles_` 缺少陣列長度上限）不在這份 spec 範圍內，將於這份 spec
  完成後另外處理。

## Further Notes

- 決策脈絡：原本評估過直接在四個底層模組的拋出點把訊息換成通用內容，不透過額外的標記/包裝機制；
  但這樣會讓 SupabaseClient、StorageClient、Embeddings 三份既有測試檔裡總共 11 個直接斷言「原始
  HTTP 狀態碼跟回應內容有沒有正確傳遞」的測試案例，失去原本要驗證的意義，必須跟著改寫測試意圖。
  改採在對外進入點做轉換的方式，可以完整保留這些既有測試，同時把「這裡的細節該不該讓外部看到」
  這個判斷放在概念上更準確的信任邊界位置——這正是這次要修的問題本身：內部細節跨越了信任邊界。
- 修正完成後，記得依專案慣例在 README.md「已知問題修復紀錄」新增對應編號條目，並回頭確認這份
  spec 有沒有跟其他既有 spec（例如 `spec_security_hardening.md`）的既有敘述衝突，需要的話補上
  Further Notes 更正說明。
