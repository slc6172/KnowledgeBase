# Spec：桌面／手機窄螢幕響應式版型

**Triage label**：`ready-for-agent`

**來源**：本次對話的 `/grilling`（三輪問答，逐項定案，設計樹全部分支走完後由使用者確認）。

## Problem Statement

這個知識庫的介面從一開始就只為桌面寬度設計——樣式表完全沒有寫過任何依螢幕寬度調整版面的規則，
頂端導覽列、搜尋列、批次操作工具列、文章詳情頁的操作按鈕、分類／標籤管理頁的節點列，全部是橫向
排列或多欄位並陳的版型。在手機瀏覽器打開這個頁面時，這些元件會互相擠壓、換行凌亂，甚至縮小到難以
點擊，實際上等於只能透過桌面瀏覽器使用。這讓「臨時想到什麼、拿起手機就能記一筆」這種個人知識庫工具
最基本的使用情境完全不可行——擁有者只能等到坐回電腦前才能新增或查閱內容。

除此之外，文章編輯器目前使用 Markdown 編輯套件的預設完整工具列（約 20 顆按鈕，包含雙欄預覽、
全螢幕這類需要寬螢幕才有意義的功能），這些按鈕在窄螢幕上不但用不到，還會佔用寶貴的垂直空間，把
真正的輸入區域往下擠壓。

## Solution

從零開始為這個專案建立一套響應式版型策略：以 768px 為界，分成桌面版型（維持現有置中內容欄寬不變）
與窄螢幕版型兩層，不另外為平板尺寸做第三套版型。窄螢幕版型的核心設計原則是「盡量套用使用者已經在
其他知名平台上熟悉的互動模式」，降低重新學習介面的成本，而不是憑空發明新的手勢或版面：

- 頂端導覽列的次要按鈕（新增文章／分類管理／標籤管理）收進一個漢堡選單抽屜，抽屜裡額外加入一個
  明確的「文章列表」項目；品牌文字維持既有的回首頁行為。
- 文章列表頁的次要篩選條件（狀態／分類／標籤）收進一個由「篩選」按鈕開啟、從螢幕底部滑入的面板；
  搜尋框跟「選取」按鈕維持常駐，不收進面板。
- 批次選取模式下的操作工具列，在窄螢幕改成固定貼在畫面最下方。
- 文章詳情頁把「編輯」維持常駐顯示，「分享」「刪除」收進一個「更多」選單，且這個選單重用跟篩選
  面板同一套「由下滑入」的共用元件，不是另外設計第二套彈出邏輯。
- Markdown 編輯器工具列全平台（桌面與手機）統一改成精簡過的常用按鈕組合，不再依斷點動態切換。
- 新增一小組手刻的行內 SVG 圖示（漢堡、更多、篩選等），取代原本容易在不同系統上顯示不一致的
  文字符號，且不引入任何外部圖示庫或新的網路依賴。

這些新增的互動模式全部封裝成共用元件（抽屜、由下滑入的面板、SVG 圖示組），讓專案以後如果需要
新增其他窄螢幕互動，可以直接套用既有元件，不用每次重新設計一套。

## User Stories

1. 身為在手機瀏覽器開啟知識庫的擁有者，我希望版面能配合手機螢幕寬度自動調整，不會出現元件互相
   擠壓、文字被裁切，或需要橫向捲動才看得到完整內容的情況。
2. 身為手機使用者，我希望原本橫排在頂端的「新增文章／分類管理／標籤管理」按鈕收進一個漢堡選單，
   點擊圖示就能展開，不會一直佔用版面寬度。
3. 身為手機使用者，我希望漢堡選單抽屜裡有一個明確的「文章列表」項目，可以直接點回文章列表，不
   需要特別去找品牌文字才能回首頁。
4. 身為手機使用者，我希望品牌文字（目前的回首頁按鈕）在抽屜之外依然可以點擊回首頁，原本的行為
   不會被拿掉。
5. 身為手機使用者，我希望搜尋框在窄螢幕上依然常駐在畫面上方、不需要額外點擊才看得到，因為搜尋
   是我最常用的操作。
6. 身為手機使用者，我希望狀態／分類／標籤這幾個篩選條件收進一個「篩選」按鈕，點擊後從螢幕底部
   滑出一個面板讓我勾選，不用一次把所有篩選欄位塞在同一排裡。
7. 身為手機使用者，我希望篩選面板點擊背景遮罩就能關閉，不需要學習額外的手勢。
8. 身為手機使用者，我希望「選取」（進入批次選取模式）這個按鈕維持獨立顯示，不會被放進篩選面板
   裡，因為這是切換模式的動作，跟篩選條件的性質不一樣。
9. 身為手機使用者，我希望進入批次選取模式後，底下出現的「刪除／設分類／加標籤」工具列固定貼在
   畫面最下方，方便單手操作，不用每次都捲回畫面最上方才找得到這些按鈕。
10. 身為手機使用者，我希望在文章詳情頁，「編輯」這個最常用的操作按鈕維持隨時看得到、不需要額外
    點擊才能找到。
11. 身為手機使用者，我希望「分享」跟「刪除」這兩個較少用、其中刪除又有風險的操作，收進一個
    「更多」選單裡，降低誤觸刪除的機率。
12. 身為手機使用者，我希望這個「更多」選單的呈現方式跟篩選面板一致（都是從底部滑出），不會在
    同一個工具裡看到兩種風格不一致的彈出選單。
13. 身為手機使用者，我希望文章內文、附件清單在窄螢幕上正常換行、寬度自動縮放，不會有內容被截斷
    或需要橫向捲動的情況。
14. 身為手機使用者，我希望文章裡 PDF 或 Office 文件的線上預覽區塊，高度會依照手機螢幕比例調整，
    不會維持桌面版的固定高度導致預覽區塊過長或過短。
15. 身為手機使用者，我希望上傳附件時可以直接用手機內建的檔案選取功能（相簿、拍照或檔案總管），
    不需要額外的操作步驟。
16. 身為在手機上新增或編輯文章的使用者，我希望 Markdown 編輯器工具列是精簡過的常用按鈕（粗體、
    斜體、標題、連結、清單等），不會出現一堆用不到、佔空間的按鈕（如雙欄預覽、全螢幕）。
17. 身為在桌面編輯文章的使用者，我希望編輯器工具列跟手機版一樣是這組精簡按鈕，兩邊操作方式一致，
    不會因為換裝置而找不到常用按鈕的位置。
18. 身為在手機上管理分類／標籤的使用者，我希望這些管理頁面的節點列（重新命名／刪除／搬移／合併
    等按鈕）在窄螢幕上會自然往下堆疊而不是被擠成一團，即使沒有針對觸控特別優化排版，至少每個按鈕
    都點得到、看得清楚。
19. 身為使用桌面瀏覽器的使用者，我希望這次的改動完全不影響原本熟悉的桌面版面配置與操作方式。
20. 身為知識庫擁有者，我希望不管用手機還是桌面開啟，都是同一個網址、同一份資料，不需要額外設定
    或切換版本。
21. 身為未來的維護者，我希望這次新增的漢堡選單、篩選面板、更多選單背後，是同一套可重用的
    「抽屜／底部滑入面板」元件跟一小組共用的 SVG 圖示，以後如果要在其他地方加類似的窄螢幕互動，
    可以直接套用，不用重新設計一套。
22. 身為未來的維護者，我希望有自動化測試防止這次定案的窄螢幕版型關鍵寫法（例如斷點寫法、共用
    元件必要的 class 或屬性）未來被意外刪除或改壞，不用每次改動都重新用肉眼在各種尺寸下複查一遍。
23. 身為使用者，我希望 `docs/preview/` 底下現有的靜態預覽檔案同步更新這次的響應式改動，讓我可以
    直接在瀏覽器的裝置模擬器裡快速檢查手機版型，不需要每次都重新部署才能看到效果。
24. 身為知識庫擁有者，我希望完成後能照著一份涵蓋各主要窄螢幕互動情境的驗收清單，親手在手機瀏覽器
    （或裝置模擬器）上逐項確認畫面正常、操作得到。

## Implementation Decisions

- **斷點策略**：只分兩層，`>=768px` 沿用現有桌面版型（置中內容欄寬不變），`<768px` 套用窄螢幕
  版型。不另外為平板尺寸設計獨立的第三層版型；縮小的桌面視窗如果落在 768px 以下，也會自然套用
  窄螢幕版型，這是預期中的行為。
- **導覽抽屜**：樣式模組新增抽屜的展開／收合樣式；前端邏輯模組新增開關抽屜的控制邏輯，抽屜項目
  為「文章列表、新增文章、分類管理、標籤管理」，其中「文章列表」是這次新增的項目，其餘三項對應
  既有按鈕的行為原封不動搬過來，不改變各自觸發的動作。品牌文字的回首頁行為維持不變，不因為抽屜
  的加入而被取代。
- **共用的「由下滑入面板」元件**：新增一組可重用的面板元件（滑入動畫、背景遮罩、點擊遮罩關閉），
  同時供「篩選面板」與文章詳情頁的「更多選單」使用，兩者是同一套元件的兩種內容，不是各自獨立
  實作。只做點擊遮罩關閉，不做拖曳手勢關閉。
- **篩選面板內容**：把既有的狀態／分類／標籤三個篩選欄位搬進面板內，欄位本身的行為（含既有的
  標籤篩選邏輯）不變，只改變其容器與觸發方式。搜尋框與「選取」按鈕維持在面板外、原本的常駐位置。
- **更多選單內容**：把文章詳情頁既有的「分享」「刪除」兩個按鈕的觸發邏輯原封不動保留，只改變其
  呈現位置——收進更多選單、由一個新增的觸發按鈕開啟。「編輯」按鈕維持在窄螢幕版型中常駐顯示，
  不進選單。
- **批次操作工具列**：窄螢幕下工具列改為固定定位在畫面底部；桌面版型（`>=768px`）維持現有的
  貼頂表現，不受影響。工具列內各個操作按鈕與下拉選單本身的行為不變。
- **圖示**：新增一小組手刻的行內 SVG 圖示，涵蓋漢堡、更多、篩選（以及依實作需要可能新增的返回
  圖示），全部內嵌在樣式或樣板模組中，不引入外部圖示庫或字型、不新增任何網路請求依賴。
- **Markdown 編輯器工具列**：明確設定一組精簡過的自訂工具列（涵蓋粗體、斜體、標題、引用、連結、
  清單、程式碼、預覽等常用項目），移除雙欄預覽、全螢幕、使用說明這類項目；這組工具列在桌面與
  手機共用同一份設定，不依斷點動態切換、不需要在斷點切換時重建編輯器實例。
- **附件線上預覽尺寸**：既有的固定像素高度（PDF 檢視區塊等）改成使用相對於視窗高度的單位，讓
  預覽區塊在窄螢幕下有合理的比例，不維持桌面版的固定高度。附件上傳的檔案選取沿用瀏覽器原生
  行為，不需要額外的前端邏輯調整即可支援手機相簿／拍照來源。
- **分類／標籤管理頁**：不特別新增收合或觸控優化邏輯，讓既有的節點列在窄螢幕下透過一般的換行／
  堆疊排版自然適應即可。
- **實作順序**：先完成「響應式基礎建設」——斷點規則、SVG 圖示組、抽屜、由下滑入面板這幾個共用
  元件與互動邏輯——再進行後續各視圖（文章列表、文章詳情、文章編輯器、分類／標籤管理）的調整。
  後續視圖的實作依賴這層基礎已經完成，不是彼此互不阻塞的垂直切分；明確的相依關係會在
  `/to-tickets` 階段展開成對應的 Parent／Blocked by 說明。
- **範圍邊界**：這次是純前端（樣板／樣式／前端邏輯）的改動，不涉及任何後端函式或資料庫層的變更，
  不需要新增或修改 `.gs` 模組，也不影響現有的密碼保護、曝光邊界等資安機制。

## Testing Decisions

好的測試只驗證外部可觀察的行為（畫面上實際呈現的結果、使用者能操作到的路徑），不綁定內部實作
細節。

- **前端沒有可用的 DOM 行為測試接縫**，延續專案既有針對這種情況已經示範過的兩種模式：
  - **靜態文字掃描測試**（讀原始碼文字斷言，前例：`ShareLinkOutputEscaping.test.js`、
    `MarkdownSanitization.test.js`）：針對這次新增的關鍵寫法——斷點規則的存在、共用面板／抽屜
    元件必要的 class 或屬性、精簡過的編輯器工具列設定——寫對應的靜態掃描測試，防止未來被意外
    刪除或改回舊版本。
  - **抽出純函式做真行為測試**（前例：`AttachmentUrlProtocolValidation.test.js` 的
    `isSafeAttachmentUrl_`）：如果實作過程中出現不依賴 DOM 的純函式（例如判斷目前是否在窄螢幕
    斷點的輔助邏輯、決定要開啟哪個面板內容的狀態判斷邏輯），比照這個模式抽出來寫真正呼叫函式
    驗證行為的測試，不因為「前端沒有測試基礎建設」就放棄這類邏輯的自動化驗證。
- **不新增任何後端測試**：這次沒有修改任何 `.gs` 模組的行為，既有 186 個測試維持不動，不需要
  額外的紅綠測試流程。
- **人工驗收清單**（比照上次資安強化，畫面實際渲染層面的行為交由使用者在瀏覽器手動確認）需要
  涵蓋：漢堡選單開合、抽屜的「文章列表」項目正確導回列表、篩選面板開關與篩選條件正確套用、
  「選取」按鈕維持獨立可點、批次工具列在窄螢幕貼底顯示、更多選單開關與「分享」「刪除」動作正常
  觸發、「編輯」按鈕常駐顯示、Markdown 編輯器工具列在桌面與手機都是同一組精簡按鈕、附件上傳
  可從手機相簿／拍照來源選取、附件線上預覽區塊在窄螢幕不跑版、分類／標籤管理頁面在窄螢幕自然
  堆疊不重疊，以及確認桌面版（`>=768px`）版面與操作方式完全沒有受到影響。
- **`docs/preview/` 靜態預覽檔案的同步維護**：這次改動樣式、前端邏輯或各視圖樣板時，對應同步
  更新現有的靜態預覽檔案內嵌的版本，讓使用者能在不部署的情況下用瀏覽器裝置模擬器快速驗收——
  這是延續既有的維護模式，不是新建的機制。

## Out of Scope

- 深色模式。
- 平板（介於桌面與手機窄螢幕之間）的獨立斷點或版型。
- 篩選面板／更多選單的拖曳手勢關閉（僅支援點擊遮罩關閉）。
- 分類／標籤管理頁面的觸控體驗優化——允許節點列在窄螢幕直向堆疊即可，不做額外的收合、手勢或
  精簡呈現。
- 附件線上預覽的觸控手勢優化（縮放、滑動等交由瀏覽器原生行為處理，不額外開發）。
- Markdown 編輯器依斷點動態切換不同工具列組合（已定案為全平台統一精簡工具列）。
- 建立完整的前端 DOM 自動化測試框架與對應的測試接縫設計（沿用既有的靜態掃描／純函式抽出模式，
  這是一個範圍更大、需要獨立討論的基礎建設決定）。
- PWA 化、離線使用、加入手機主畫面等原生應用程式相關能力。
- 任何後端（`.gs` 模組）或 Supabase 端（`schema.sql`）的變更。

## Further Notes

- 這次是純前端改動，不涉及 `schema.sql` 或任何 Supabase 端變更，部署時 Supabase 端不需要做
  任何事，延續上一輪資安強化的慣例。
- 新增的共用元件（抽屜、由下滑入面板、SVG 圖示組）是這次最重要的架構決定；後續如果有新的窄螢幕
  互動需求，應該優先考慮重用這些元件，而不是重新設計一套新的呈現方式。
- 依 `/grilling` 定案的實作順序，「響應式基礎建設」需要先完成，後續各視圖的調整都建立在這層
  基礎之上，顆粒度與相依關係會在 `/to-tickets` 階段展開成明確的 Parent／Blocked by 關係，跟
