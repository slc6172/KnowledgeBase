# Spec：權限驗證與輸出跳脫資安強化

**Triage label**：`ready-for-agent`

**來源**：`gas-supabase-knowledge-base-review.md`（安全性審查報告）H1、H2、M1、M2、M3、M4 六項發現，
經 grilling 對談逐項定案。

## Problem Statement

這個知識庫工具設計上只有擁有者一個人能用寫入密碼保護新增/修改/刪除操作，讀取功能則刻意設計成任何人
都能直接呼叫。但目前這個「密碼保護」只是前端 UI 的一個慣例——底層真正執行寫入、以及直接代理整個
資料庫存取的函式，因為平台的曝光規則，其實不需要任何密碼就能被直接呼叫。這代表：只要有人能讓擁有者
的瀏覽器對這個頁面執行一段惡意 JS（例如透過一個偽裝成分享連結、內含惡意內容的網址），就能繞過密碼，
直接清空或竄改整個知識庫，擁有者本人可能完全沒有察覺。

除此之外，分享連結功能本身就存在一個輸出跳脫的漏洞，會讓惡意連結裡的內容變成真正可以執行的程式碼；
文章內文與部分附件在顯示時也沒有經過消毒，如果內容來源不完全可信（例如複製貼上網路上的東西），一樣
可能在讀者端執行不該執行的程式碼；附件的自訂網址也沒有限制協定，理論上可以存入一個看起來像連結、
點下去卻會執行程式碼的網址；而一個原本只該由擁有者手動執行一次的初始化功能，也因為同樣的曝光規則，
任何人都能觸發，觸發後會把包含密碼在內的所有機密設定重設成一組公開已知的預留值。

## Solution

把「密碼才能寫入」這件事從單純的前端慣例，變成平台真正會強制執行的邊界：所有寫入操作與泛用資料庫
代理函式都改成只能透過密碼驗證的唯一入口呼叫，不再存在能繞過密碼直接觸發的路徑；分享連結裡使用者
可控的內容改用平台本身的自動跳脫機制輸出，不再可能被用來注入可執行內容；文章內文與可能含有他人來源
內容的附件在顯示前一律先經過消毒；附件網址限制只能是一般網頁連結；只該手動執行一次的初始化功能不再
是任何呼叫端都能觸發的公開端點。修好之後，即使有人成功讓擁有者開啟一個惡意連結，也無法再繞過密碼
存取或竄改資料。

## User Stories

1. 身為知識庫擁有者，我希望所有會修改資料的操作都一定要驗證寫入密碼，這樣即使我不小心點到一個
   惡意連結，攻擊者也沒辦法繞過密碼竄改或刪除我的文章。
2. 身為知識庫擁有者，我希望「直接對資料庫下任意指令」這種泛用能力不會被暴露成任何頁面載入時就能
   呼叫的公開端點，這樣就算密碼保護有遺漏，攻擊面也不會擴大到整個資料庫。
3. 身為知識庫擁有者，我希望分享連結裡的參數不管內容是什麼，都不可能在我的瀏覽器裡變成真正執行的
   程式碼，這樣我可以放心點開別人傳給我、看起來是分享連結格式的網址。
4. 身為文章讀者（透過分享連結開啟公開文章的任何人），我希望瀏覽文章內容時不會意外執行到內容裡
   夾帶的程式碼，這樣單純閱讀文章不會有被植入惡意程式碼的風險。
5. 身為知識庫擁有者，我希望上傳/預覽 Markdown 附件檔案時，內容一樣會先被消毒過再顯示，跟文章內文
   享有同等的保護。
6. 身為知識庫擁有者，我希望 AI 問答功能顯示的回答內容也經過同樣的消毒流程，不會因為回答裡引用了
   帶有惡意內容的文章片段而執行到不該執行的程式碼。
7. 身為知識庫擁有者，我希望附件的自訂網址欄位只能存一般的網頁連結，不能存入看起來像連結、點下去
   卻會執行程式碼的網址。
8. 身為知識庫擁有者，我希望存附件網址時如果格式不對，能在畫面上馬上看到清楚的錯誤訊息，不用等到
   送出後才發現存錯了。
9. 身為知識庫擁有者，我希望「重設所有機密設定」這種只該手動執行一次的初始化功能，不會被暴露成
   任何人（或任何注入的程式碼）都能觸發的端點，避免我的密碼跟金鑰被重設成公開已知的值。
10. 身為未來的維護者，我希望以後新增類似「只該由開發者手動執行一次」的函式時，有一個機制會提醒我
    別讓它意外暴露出去，而不是要等到下一次資安審查才會發現。
11. 身為未來的維護者，我希望以後在程式碼裡讀到跟這次修正相關的說明註解時，不會因為註解裡寫出真正
    有作用的語法片段，而讓 Apps Script 的樣板引擎把註解內容當成真的程式碼執行。
12. 身為未來的維護者，我希望能在專案既有的「已知問題修復紀錄」裡查到這批問題的根因與修法，不用
    重新踩一次同樣的坑。
13. 身為知識庫擁有者，我希望這次修正完成後，能照著一份包含資安情境的驗收清單，親手驗證分享連結、
    文章內容、附件網址這幾個原本有問題的地方，現在確實安全了。

## Implementation Decisions

- **寫入操作與資料庫代理函式的曝光邊界**：Auth 白名單模組列出的全部寫入函式，以及 SupabaseClient
  模組對外提供的全部泛用資料庫存取函式（含底層的泛用 REST 代理），一律改成平台規則下不會被自動
  暴露給前端呼叫端的私有函式；唯一允許外部呼叫的入口是 Auth 模組現有的密碼驗證轉呼叫機制，其對外
  可見的操作名稱（前端呼叫時用的字串）維持不變，前端呼叫方式不需要跟著調整。不額外在各個函式內部
  重複做密碼檢查——曝光邊界本身就是強制執行的防線，不需要疊加第二層。
- **分享連結參數的輸出方式**：分享連結帶入的文章 ID 這類使用者可控的值，改成先寫入頁面上某個既有
  元素的資料屬性，透過平台本身「會自動依輸出情境跳脫」的樣板標籤輸出（而不是目前這種手動組字串、
  再用不跳脫樣板標籤直接輸出的做法）；前端啟動邏輯改成從該屬性讀值，下游判斷邏輯維持不變。
- **內容顯示前的消毒**：文章內文、Markdown 檔案型附件的預覽內容、AI 問答的回答內容，這三個目前把
  Markdown 轉換結果直接指定給頁面元素內容的地方，改成先經過一套業界標準的 HTML 消毒處理再顯示。
  新增的消毒函式庫透過既有的第三方函式庫載入方式引入，跟專案目前載入 Markdown 渲染/語法上色/
  編輯器函式庫的方式一致。
- **PostgREST filter 組裝**：SupabaseClient 模組新增一組共用的 filter 組裝輔助函式，統一處理值的
  URL 編碼；所有目前用手動字串相加組出等於比對、清單比對這類過濾條件的呼叫端都改用這組輔助函式，
  不只限於目前已知會吃自由文字輸入的欄位，任何組進過濾條件字串的值都一併納入，作為縱深防禦。
- **附件網址協定驗證**：新增附件自訂網址時，伺服器端只接受一般網頁連結協定開頭的網址，其餘一律
  拒絕並回傳明確錯誤；前端存檔表單在送出前先做同樣的檢查，提早給出錯誤訊息，伺服器端驗證才是真正
  的防線。
- **一次性初始化/診斷函式**：目前只該由開發者在 Apps Script 編輯器手動觸發一次的初始化函式，以及
  純診斷用的設定檢查函式，一併改成平台規則下不會被自動暴露的私有函式；在函式定義附近以文字說明
  改成手動觸發的替代做法（例如暫時調整函式名稱後執行完再改回、或另外包一個用完即刪的臨時觸發
  函式），不使用任何真正具有語法作用的角括號寫法描述這件事。
- **註解撰寫限制**：這次新增或修改的所有說明性註解，一律不得寫出任何完整、具有實際語法作用的角
  括號組合（不限於 script 標籤，任何會被 Apps Script 樣板引擎當成真正指令解析的寫法都算），一律
  改用中文描述取代。

## Testing Decisions

好的測試只驗證外部可觀察的行為（呼叫入口的結果、對外部服務送出的請求內容），不綁定內部實作細節。

- **後端邏輯**：延續專案既有測試模式——以「唯一對外發送網路請求的接縫」為假資料替換點，驗證上層
  函式組出的請求內容與回傳結果處理是否正確；每個模組已有對應測試檔，這次新增/調整的行為（filter
  值編碼結果、附件網址協定拒絕邏輯）在對應模組的既有測試檔案裡補上對應案例。
- **曝光邊界的迴歸防護**：新增一個獨立的靜態檢查測試，直接讀取所有後端模組的原始碼文字，斷言這批
  改成私有的函式宣告都確實帶有平台規定的私有字首；用意是彌補「本地測試環境無法真正模擬平台曝光行為」
  這個既有限制，讓同類問題不用等到下一次人工審查才會被發現，測試失敗時列出目前不符合規則的函式清單。
- **前端**：延續專案既有慣例（語法檢查 + 手動驗收清單），不新增前端自動化測試框架——這是一個範圍
  更大、需要獨立討論測試接縫設計的基礎建設決定，不適合包在這次資安修正裡一併處理。這次手動驗收
  清單需要明確補上資安相關的驗收情境，至少涵蓋：帶有可執行內容片段的分享連結參數、文章內文/附件
  預覽裡帶有可執行內容的 Markdown 內容、附件網址欄位填入非網頁連結協定的網址，逐一確認畫面上不會
  真的執行到任何非預期的程式碼，且既有的語法上色等正常顯示效果不受影響。

## Out of Scope

- 把三層節流(一般讀取/語意搜尋/密碼鎖定)的 CacheService 計數器 key 拆成每 IP/session 各自一份，
  而不是目前全站共用同一把固定字串 key（2026-09 這輪 `/mycr` 複查才第一次被問出來，細節與理由見
  `Auth.gs` 該函式上方註解第 3 點，以及 README 已知問題修復紀錄第 41 條）。
- 批次操作/刪除文章時附件清理迴圈的批次化效能優化（審查報告 L3，目前使用規模下影響有限）。
- 前端建立完整的自動化測試框架與對應測試接縫設計（見 Testing Decisions，需要獨立討論）。

  這份 spec 原本的討論都是針對個別函式(例如某個函式該不該有密碼、該不該
  有節流)，沒有從「Apps Script 平台規則本身」的角度，把所有頂層函式完整
  窮舉過一次、逐一確認曝光邊界。`/mycr` 這輪做了這件事，確認目前 16 個
  暴露給 google.script.run 的頂層函式全部都有對應防護，`callProtected` 的
  分派機制本身是固定 `switch` 白名單、不是動態函式查找，沒有找到繞過空間；
  同時找到兩個「頻率有節流擋、但單次請求大小沒擋」跟「批次操作的既有保護
  模式沒被一致套用」的落差並修掉。細節見 README 已知問題修復紀錄第
  48–51 條。

- **逐行語意校對(不是套規則掃描)找到的落差(2026-09)**：前面幾輪
  `/mycr` 大多是「套用某條規則或某個角度去找符合特定模式的問題」，這輪
  換成真的逐行讀過 `Articles.gs`/`Categories.gs`/`SupabaseClient.gs`/
  `schema.sql`/`JavaScript.html`，順著資料流動去想「這個值/這個分支最後
  真的執行到的時候會發生什麼事」。找到的問題都不是資安漏洞（不會多洩漏
  什麼），是邏輯正確性/一致性層面的落差：`eqFilter_`/`inFilter_` 只做
  URL 編碼、沒有做 PostgREST 自己要求的保留字元跳脫（**這一項的第一次
  查證方式有誤——部署到真實 Supabase 專案後發現對 `eqFilter_` 的修法會
  造成更嚴重的迴歸（UUID 欄位查詢直接 400），已經復原；後續用 Context7
  重新查證 + 使用者對真實 UUID 主鍵做過一次唯讀測試確認，`inFilter_`
  這半邊其實是對的，已經重新修好，`eqFilter_` 維持不動，細節見 README
  第 65、66 條**）；
  `moveCategory_`/`filterArticleIdsByTags_`（含 SQL 端
  `hybrid_search_articles` 的對應版本）兩處存在性檢查/去重不一致；前端
  分類刪除少了跟其他三個刪除動作不一致的 `window.confirm()`——這三項
  維持修復狀態，沒有受到上面那項復原影響。細節見 README 已知問題修復
  紀錄第 57–62、65 條。

- 這批問題全部不是已知並接受的既有設計取捨——專案現有的設計文件與規格文件都沒有討論過「平台的
  曝光邊界」「樣板標籤的輸出跳脫情境」這兩件事，屬於規劃階段就遺漏、這次審查才第一次被發現的落差。
- 修正完成後，需要比照專案「已知問題修復紀錄」現有條目的格式，新增條目記錄這批問題的根因與修法，
  方便以後查閱、避免同類問題在未來的功能開發中重演。
