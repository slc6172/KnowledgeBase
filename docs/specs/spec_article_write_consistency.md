# Spec:文章寫入路徑不再被公開讀取節流牽連,且不再有部分提交

**Triage label**:`ready-for-agent`

**來源**:`mycr-20260921-060513.md`(全新複掃報告)Finding F-01,經 `/grilling` 對談逐項定案(2026-09-22)。

## Problem Statement

建立、編輯、發布/取消發布、刪除文章這幾個寫入操作,內部會呼叫**跟匿名訪客共用同一份節流額度**的公開
讀取函式(`getArticle`、`listAttachments`)——這層節流本來是為了保護「不需要登入就能連線」這個部署
方式下,Apps Script 本身的 UrlFetch 每日配額不會被匿名訪客燒光,設計上完全沒考慮到寫入路徑也會內部
呼叫到同一批函式。這份共用的每小時額度一旦被用滿(不論是匿名訪客的正常瀏覽量,或是分享連結被同時
打開),擁有者自己的編輯操作就會在**資料庫已經寫入之後**才收到「目前使用量過大」的錯誤——編輯文章
會顯示失敗但內容其實已經改了、發布文章會顯示失敗但狀態其實已經變成已發布,而且這兩種情況下,原本
該接著重新產生的語意搜尋向量(embedding)都會因為函式提早拋錯而被跳過,悄悄留下一個過期的搜尋索引,
直到下一次成功儲存才會更新。建立文章顯示失敗但其實文章已經寫進資料庫,擁有者重試還會建立出重複的
文章。

即使把節流這個特定觸發點修好,同一種「資料庫已經寫入、但後續步驟才失敗」的問題還會以另一種方式出現:
更新已發布文章的內容、或把草稿發布為已發布時,目前的寫法都是先把內容/狀態寫進資料庫,再呼叫 Gemini
重新產生 embedding——只要 Gemini 這一步因為任何原因失敗(服務中斷、配額用盡、逾時),資料庫裡的內容
或狀態已經確定改變了,但 embedding 沒有更新,使用者看到的結果跟節流觸發時一模一樣。

## Solution

把「這個讀取要不要被節流」跟「這個讀取實際上要抓什麼資料」拆開:新增不節流的內部讀取,只給寫入路徑
自己用;公開讀取函式(`getArticle`/`listAttachments`)對外的行為完全不變,一樣要通過節流檢查,只是
內部改叫這個新的內部版本去真正抓資料。這樣擁有者自己的寫入操作,就不會再被匿名訪客用掉的額度連累。

同時,把兩條真的會呼叫 Gemini 的寫入路徑——更新已發布文章的內容、把草稿發布為已發布——重新排序:
先把新的 embedding 算出來,**確認 Gemini 這一步成功之後**,才用單一次資料庫寫入把內容/狀態跟新
embedding 一起送出去。這樣不管是節流還是 Gemini 本身出問題,都會在任何資料庫寫入發生之前就失敗,
不會再留下「部分提交」的狀態:要嘛使用者要的東西整組一起生效,要嘛完全沒發生。其餘不涉及 Gemini 的
路徑(建立文章、刪除文章、只改分類或標籤、取消發布)維持現在的呼叫順序不變——它們原本就沒有部分
提交的風險,唯一的問題只有節流誤傷,前段的內部讀取繞過就已經完全解決。

## User Stories

1. 身為正在編輯文章內容的擁有者,我希望這次編輯要嘛整組成功(內容存檔、搜尋索引也一起更新),要嘛
   整組失敗(什麼都沒變),不要出現編輯器裡看到的內容跟實際能被搜尋到的內容對不起來的狀況。
2. 身為正在把草稿發布出去的擁有者,我希望發布這個動作要嘛整組成功(狀態變成已發布、embedding 也
   一起產生),要嘛整組失敗(文章繼續留在草稿),不要出現一篇「已發布」但搜尋不到的文章。
3. 身為正在建立新文章的擁有者,我希望即使當下有很多匿名訪客正在瀏覽這個知識庫,建立文章這個動作
   還是能穩定成功,不會被別人的讀取流量卡住。
4. 身為正在編輯、發布或刪除文章的擁有者,我希望即使這一個小時的匿名讀取額度已經被訪客流量用滿,
   我管理自己內容的操作還是能正常運作,不會被別人的使用量鎖住。
5. 身為正在刪除文章的擁有者,我希望刪除前用來找出要一併清掉的附件檔案這個檢查,也不會被同一份
   公開讀取額度卡住,理由跟上一條一樣。
6. 身為瀏覽這個知識庫的匿名訪客,我希望保護部署本身 UrlFetch 配額的每小時額度機制,行為跟現在完全
   一樣繼續生效,不要因為這次修正被悄悄關掉或放寬。
7. 身為擁有者,當我只改文章的分類或標籤、沒有動到標題或內文時,我希望這次儲存的行為(呼叫次數、
   流程)跟現在完全一樣,因為這種情況本來就不需要重新產生搜尋索引。
8. 身為擁有者,當我把一篇已發布的文章改回草稿時,我希望這個動作的行為跟現在完全一樣,因為取消發布
   本來就不涉及重新產生 embedding。
9. 身為擁有者,當我在編輯一篇已發布文章的內容、而 Gemini 服務當下剛好不可用或回傳錯誤時,我希望
   看到清楚的失敗訊息,而且我這次的內容編輯**沒有**被套用,而不是編輯悄悄生效、但搜尋索引留在
   舊的狀態。
10. 身為擁有者,當我在發布一篇文章、而 Gemini 服務當下剛好不可用或回傳錯誤時,我希望發布這個動作
    完全不會生效,而不是文章的狀態已經變成「已發布」、但其實從來沒有真正被 embedding 過。
11. 身為擁有者,在上面兩種情況失敗之後重試,我希望可以放心重試,不用擔心上一次失敗的嘗試留下什麼
    需要我自己手動清理的殘留狀態。
12. 身為維護者,我希望「任何人都能呼叫的公開入口」跟「寫入路徑內部用來確認目前狀態的內部讀取」
    這兩者之間的分野清楚、命名一致,這樣以後有人要加新的寫入功能時,不會不小心又直接呼叫到公開、
    會被節流的版本,重蹈這次的覆轍。
13. 身為維護者,我希望「公開讀取函式本身要受節流保護」這件事(上一輪修正加進去的行為)這次完全
    不受影響,繼續維持現狀,因為那是正確、刻意要保留的保護機制。
14. 身為維護者,我希望之後想查這次修正的來龍去脈時,能在專案既有的「已知問題修復紀錄」裡找到,
    不需要單靠原始碼自己重新推敲一次。

## Implementation Decisions

- **新增不節流的內部讀取,只給寫入路徑用**:一個用來讀單篇文章(供 `createArticle_`/
  `updateArticle_`/`setArticleStatus_` 使用)、一個用來讀某篇文章的附件清單(供 `deleteArticle_`
  使用)。公開的 `getArticle`/`listAttachments` 保持現在「先節流、再讀取」的行為不變,只是內部改
  委派給這兩個新的內部版本去真正抓資料——對外的呼叫方式、回傳形狀、被外部直接呼叫時仍會受節流
  保護,這三件事都不變。
- **不是新模組,是既有檔案裡的一般內部函式**:這兩個新函式就放在原本 `Articles.gs`/`Attachments.gs`
  裡,命名方式(底線字首)比照檔案裡其他內部函式的既有慣例,不是要新增一層架構。
- **建立文章路徑**:只套用「內部讀取繞過節流」這一個修正,呼叫順序不變——新文章一律是草稿,不會
  觸發 embedding,沒有部分提交的風險。
- **刪除文章路徑**:只套用「內部讀取繞過節流」這一個修正,呼叫順序不變——刪除從不涉及 Gemini,
  查附件清單這一步本來就發生在真正刪除之前,沒有部分提交的風險。
- **編輯文章路徑,沒有動到標題/內文,或文章不是已發布狀態**:只套用「內部讀取繞過節流」這一個
  修正,呼叫順序不變——這種情況下從不會觸發 Gemini 呼叫,唯一的風險就是節流誤傷,前面的繞過已經
  完全解決。
- **編輯文章路徑,動到標題和/或內文、且文章是已發布狀態**:重新排序——先用內部讀取取得目前的
  標題/內文,跟這次傳入的修改欄位合併成最終要拿去產生 embedding 的文字(標題或內文只要有一個沒
  被這次修改帶到,就沿用目前的值,合併規則跟現在「讀回後才判斷」的結果完全一致),在**碰資料庫
  之前**先呼叫 Gemini 算出新的 embedding,成功之後才用**單一次**更新,把這次修改的欄位(標題/
  內文/分類)跟新的 embedding 一起寫進去。標籤同步(獨立的資料表)不受這次重新排序影響,維持現在
  「主要內容更新完之後才同步標籤」的順序不變。
- **發布文章路徑(狀態改成已發布)**:比照上一條重新排序——先用內部讀取取得目前的標題/內文,在
  碰資料庫之前先呼叫 Gemini,成功之後才用單一次更新把 `status: 'published'` 跟新的 embedding
  一起寫進去。
- **取消發布路徑(狀態改成草稿)**:只套用「內部讀取繞過節流」這一個修正,呼叫順序不變——取消
  發布現在不會觸發 embedding,之後也不會,沒有理由重新排序。
- **存在性檢查跟著重新排序自然變得更早**:兩條重新排序過的路徑,現在會在任何寫入動作發生之前,就
  先用內部讀取確認文章存在(讀不到會拋出跟現在一樣的「找不到文章: <id>」錯誤,只是時間點從「寫入
  之後的讀回」提早到「寫入之前」)。維持原順序的路徑,存在性檢查方式跟現在一樣,靠寫入之後的內部
  讀回,不需要另外加一道檢查——這些路徑唯一的問題只有節流,繞過就已經解決。
- **回傳形狀完全不變**:所有寫入函式回傳的資料形狀(完整、帶 join 的文章物件,或是刪除確認物件)
  跟現在一樣,這次修正只改變內部呼叫順序跟哪些呼叫要受節流,不改變回傳給呼叫端的內容。
- **不動公開函式簽章、密碼保護的分派層、節流本身的設定**:額度大小、時間窗口、CacheService 的
  key 格式都不變——這次修正只改變「誰要受這個既有額度限制」,不改變額度機制本身。

## Testing Decisions

- 好的測試驗證外部可觀察的行為:比照這個專案既有的做法,用假的 `httpFetch_` 斷言實際發出的請求
  順序、方法、payload,以及函式最終的回傳值或拋出的錯誤——不綁定用了哪個內部函式名稱。
- 既有的節流測試(`test/Auth.test.js`、`test/Articles.test.js`、`test/Attachments.test.js` 裡
  對 `getArticle`/`listArticles`/`listAttachments`/`listFolders` 的節流斷言,做法是預先把共用的
  `CacheService` 假物件裡的計數器灌到上限)是這次新增測試的既有範例,直接沿用同樣的手法,套用在
  四個寫入函式上。
- 四個受影響的寫入函式(`createArticle_`、`updateArticle_`、`deleteArticle_`、`setArticleStatus_`)
  各補一個新測試:把共用節流計數器灌到上限,呼叫該函式,驗證它**仍然完整成功**(該發生的寫入有
  發生、回傳值正確),而不是拋錯——這是這次修正要解的問題最直接的迴歸測試。
- `updateArticle_`(改已發布文章的內容)跟 `setArticleStatus_('published')` 各補一個測試:模擬
  Gemini 呼叫失敗(比照既有「embedding error propagation」測試的做法),驗證新的順序下,失敗發生
  時**完全沒有任何一次 PATCH 打到 articles 資料表**——也就是函式在真正寫入資料庫之前就先失敗,
  不是寫入之後才失敗。
- 目前有三個既有測試,斷言的正是「重新排序之前」的呼叫順序跟 payload 形狀,要跟著改寫成新的順序
  跟單一次合併寫入的 payload,而不是原封不動保留或另外新增一份重複的測試:
  - `updateArticle` 底下的「regenerates embedding when content_md changes on a published
    article」
  - `embedding error propagation` 底下的「a non-2xx Gemini response makes
    setArticleStatus_('published') throw」——這個測試目前斷言的其實是這次要修的 bug 本身(狀態
    已經寫死已發布,Gemini 才失敗,函式才拋錯);改寫後要斷言修好的行為。
  - `setArticleStatus` 底下的「publishing updates status, fetches the article, and triggers
    embedding exactly once」
- 其餘既有測試(`updateArticle_`/`deleteArticle_`/`setArticleStatus_` 裡不涉及上面兩條重新排序
  路徑的其他案例、`createArticle`、`batchDeleteArticles`/`batchSetArticlesCategory`/
  `batchAddTagsToArticles`、`test/PrivateFunctionExposure.test.js`)預期維持全部通過、不需要修改
  斷言內容——它們都沒有預先灌爆節流計數器,拿掉內部呼叫的節流檢查不會改變它們斷言的呼叫次數或
  payload。
- `test/PrivateFunctionExposure.test.js` 既有的靜態掃描(斷言所有頂層函式宣告都帶底線字首)已經
  會自動涵蓋新增的這兩個內部函式,不需要為此另外補測試,只需要確認新函式的宣告方式跟現有內部函式
  一致,讓這個既有掃描的假設繼續成立。

## Out of Scope

- `syncArticleTags_` 自己的部分失敗風險(文章內容已經更新、但標籤同步中途失敗)——對談過程中
  確認這是另一個、還沒被稽核過的多步驟寫入問題,留給以後的 finding/spec 另外處理,不併入這次。
- 公開讀取節流本身的機制(額度大小、時間窗口、額度本身是否真的對應到它要保護的每日配額——這是
  mycr 報告另一條獨立的 F-08)——這次修正只改變「哪些呼叫要受這個既有額度限制」,不改變額度
  機制本身。
- 修正完之後、極低機率仍會發生的情況:所有寫入都已經成功之後,最後那次(現在也已經是內部、不
  節流的)讀回,剛好遇到 Supabase 真的斷線——這個情況下函式維持現在的行為,直接拋錯;要不要為此
  設計一個「已經存成功、只是讀不回最新狀態」的降級回應,是獨立的前端 UX 決策,不屬於這次範圍。
- `batchSetArticlesCategory_`、`batchAddTagsToArticles_`——對談過程中確認過,兩者都不會內部呼叫
  受節流的公開讀取函式(前者直接操作 `category_id`、不透過 `updateArticle_`;後者直接讀寫
  `article_tags`),不受這個問題影響,這次不需要改動。`batchDeleteArticles_` 呼叫
  `deleteArticle_`,會自動繼承這次的修正,不需要另外改動。
- `listFolders`、`listCategories`、`listTags`、`countTagUsage`、`getSignedAttachmentUrl`、
  `getTextAttachmentContent`、`searchArticles`、`getRelatedArticles`——確認過都不會被任何寫入
  路徑內部呼叫,不在這次範圍內。

## Further Notes

- 決策脈絡——為什麼只有兩條路徑要重新排序:對談初期曾經考慮過讓所有寫入路徑都改成「先內部讀取、
  再寫入」的統一結構,後來逐一核對 `test/Articles.test.js` 裡各個既有測試實際記錄的呼叫序列跟
  次數才發現,只有真的會呼叫 Gemini 的兩條路徑需要重新排序;其餘路徑(尤其是取消發布)如果也套用
  同樣的重排,反而會憑空多一次不必要的內部讀取(取消發布現在是「寫入→讀取」共 2 次,若比照重排
  路徑改成「讀取→寫入→讀取」會變成 3 次)。維持現狀的路徑,唯一問題只有節流誤傷,單靠內部讀取
  繞過就已經完全解決,不需要額外的重新排序。兩條真的重新排序的路徑,呼叫次數跟現在完全一樣(4
  次)——多出來的一次內部讀取,剛好被「原本分兩次寫入合併成一次」抵銷掉。
- 修正完成後,依專案慣例在 `README.md`「已知問題修復紀錄」新增對應編號條目(目前到第 77 條),
  格式比照 `spec_error_handling.md` 對應條目的寫法,簡短記錄決策脈絡跟驗證方式。
- 同一輪 mycr 報告(`mycr-20260921-060513.md`)裡跟 `Articles.gs` 有關的其他 finding(F-04:
  標籤篩選查詢的網址長度問題、F-06:前端非同步回應過期問題)是完全獨立的問題,不在這份 spec 的
  範圍內,之後需要的話應該分開開票處理。
