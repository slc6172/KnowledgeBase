# Spec：介面淡雅化與視覺一致性優化

**Triage label**：`ready-for-agent`

**來源**：本次對話的 `/grilling`（兩輪問答，並在過程中用 `uiux` 技能查證資料庫、直接讀原始碼查證現況，逐項定案後由使用者確認）。

## Problem Statement

這個專案的視覺基底其實已經不差——暖色調的米杏底色、墨綠主色、黃銅金點綴、襯線標題字，這組合本身
就不是常見的「AI 生成感」冷灰藍 SaaS 風格。但整個介面是分好幾輪、針對不同功能陸續加上去的（搜尋、
批次操作、分享、附件、RAG 問答、響應式版型……），視覺規則本身沒有被系統性地檢視過：有些地方靠顏色
標記資訊（分類色點、標籤底色），有些地方不靠；主要動作用實心填滿按鈕，但同一顆 `.btn-primary` 也
被拿去用在搜尋、新增分類、行內確認這類頻繁的操作性按鈕上，導致畫面上同時有好幾種「深色實心按鈕」
互相搶視覺重量；語意化的顏色 token 也不完整（例如疊在色塊上的白色文字目前是寫死的 `#FFFFFF`，沒有
對應的 token）。這些不一致累積起來，讓畫面沒有現在說的「淡雅」該有的克制感與層次感。

## Solution

不是打掉重練，而是在現有的暖色調性上做一輪系統性的精修，讓整個介面（桌面與手機窄螢幕）在色彩、
按鈕層級、卡片/邊框語言上有一致、克制的規則，操作手感貼近 Notion / Craft 這類知識庫工具——輕卡片、
細邊框、留白多、色彩只用在真正需要快速辨識的地方。具體做法：微調既有色票（降低飽和度、略微加亮，
不是換色），把色彩使用範圍收斂到只有狀態徽記（已發布/草稿）保留顏色識別，分類色點與標籤底色改成
中性灰階；按鈕分成「少數關鍵動作用實心填滿」跟「其餘操作性按鈕用更輕量的樣式」兩個層級；補上目前
缺的語意化「on-color」token。這次的範圍不含深色模式（先只做亮色）、不含卡片陰影的大改（查證後
確認文章卡片本身其實已經是無陰影的細邊框樣式，不需要額外處理，只有真正的浮動面板——導覽抽屜、
篩選面板、更多選單、下拉建議清單、密碼保護彈窗——維持原本的陰影，這些屬於「浮在內容之上」的元件，
陰影是合理的慣例，不在「淡雅化」要收斂的範圍內）。系統層級的 token 規則一次定調後，套用到各畫面
依優先順序分票執行：先套到最近才做的共用元件（導覽抽屜/篩選面板/更多選單）做示範，再依序套到文章
列表、文章詳情頁、文章編輯器、分類/標籤管理頁。

## User Stories

1. 身為使用這個知識庫的人，我希望整體畫面的色彩比現在更淡、更低飽和度，質感更接近紙感/文具感，
   而不是變成另一種常見的冷灰藍 SaaS 風格。
2. 身為使用者，我希望文字、按鈕邊框、次要文字這些元素的顏色比現在更輕一階，層次感更細緻，但文字
   本身的可讀性、對比度不因此變差。
3. 身為使用者，我希望狀態徽記（已發布/草稿）維持原本鮮明的顏色，因為這是我最需要一眼判斷的資訊。
4. 身為使用者，我希望分類色點、標籤 chip 底色改成中性灰階，靠文字本身辨識，不再靠一堆不同顏色
   區分，畫面看起來更乾淨。
5. 身為使用者，我希望只有真正關鍵的少數動作（例如發布文章、新增文章、密碼保護確認）才用深色實心
   填滿的按鈕，一眼就能看出這是這個畫面上最重要的動作。
6. 身為使用者，我希望其餘比較頻繁的操作性按鈕（搜尋、新增分類、篩選、選取、更多、行內確認重新
   命名等）改用比較輕量的樣式，不會每個按鈕都用同樣強的視覺重量互相搶注意力。
7. 身為使用者，我希望危險操作（例如刪除文章、刪除分類/標籤）維持現有清楚的警示色，不因為「減少
   色彩使用」而被削弱到不容易辨認。
8. 身為使用者，我希望這些視覺調整在桌面和手機窄螢幕上都一致地套用，不會有一邊調過、一邊沒調的
   情況。
9. 身為使用者，我希望最近才做的導覽抽屜、篩選面板、更多選單這些元件，視覺上（顏色、按鈕樣式）
   也套用同一套新規則，跟其他畫面一致，不會看起來像是不同時期做的東西拼在一起。
10. 身為使用者，我希望這些浮動面板（導覽抽屜、篩選面板、更多選單、下拉建議清單、密碼保護彈窗）
    維持原本「浮在內容之上」該有的陰影，不會被誤套用成跟一般卡片一樣完全平面、分不清層次。
11. 身為使用者，我希望文章卡片、相關文章卡片這類內容卡片維持現有乾淨的細邊框樣式（查證後這部分
    其實已經符合這次想要的方向，不需要改動）。
12. 身為使用者，我希望這次的視覺調整不會意外改掉任何按鈕、連結、表單原本的實際功能，純粹是外觀
    上的調整。
13. 身為使用者，我希望中文標題襯線字（Noto Serif TC）維持現有的用法，只用在少數大標題，不擴大
    使用範圍，也不拿掉，因為現有的用法本身就已經是合理的取捨，不是這次真正該解決的問題。
14. 身為未來的維護者，我希望這次新增或調整的顏色、按鈕樣式都收斂成語意化的 design token（例如
    疊在色塊上的文字顏色有專門的 token，不再寫死 `#FFFFFF`），之後要再調整風格時改一個地方就好，
    不用到處找寫死的顏色值。
15. 身為未來的維護者，我希望有自動化測試防止這次定案的顏色使用範圍（哪些元素該有顏色、哪些不該
    有）未來被意外加回去，不用每次改動都重新用肉眼複查一遍整個專案。
16. 身為未來的維護者，我希望有自動化測試確認新的 design token 確實被定義、樣式表裡沒有新增寫死
    的 hex 值繞過這些 token。
17. 身為使用者，我希望這次調整先只做亮色版本，不會因為同時處理深色模式而拖慢進度，深色模式之後
    有需要再另外討論。
18. 身為使用者，我希望套用順序是先在最近做的共用元件（導覽抽屜/篩選面板/更多選單）上示範新規則
    怎麼套用，再依序套到文章列表、文章詳情頁、文章編輯器、分類/標籤管理頁，這樣後面的畫面可以
    直接參照前面已經套用過的例子，不用每個畫面重新解讀一次規則。
19. 身為使用者，我希望完成後能透過 `docs/preview/Preview.html` 這份既有的靜態預覽檔案，直接在
    瀏覽器裡對照新舊視覺效果，不需要每次都重新部署才能看到結果。

## Implementation Decisions

- **色彩 token 微調**：在既有的 `:root` 色彩 token 上做以下調整（不新增/不刪除既有色票的定位，
  只調數值）：主色调深一階的墨綠、次要文字顏色、邊框顏色都各自略微降低飽和度或加亮一階，讓畫面
  整體更淡；背景色維持不變（已經足夠淡雅，不需要再調）。點綴色（黃銅金）數值同樣略微調淡，且依
  下一條「色彩使用範圍收斂」決定，實際出現的頻率會比現在低。
- **新增語意化 on-color token**：新增一組「疊在色塊背景上的文字顏色」token（對應主色、點綴色、
  危險色各一個），取代目前唯一一處寫死的白色文字，讓「文字要疊在什麼顏色的背景上」這件事有明確
  對應的變數可查，不用每次都用肉眼猜對比度夠不夠。
- **色彩使用範圍收斂**：只有狀態徽記（已發布/草稿）維持現有的顏色識別；分類色點、標籤 chip 底色
  改成中性灰階樣式，靠文字本身辨識，不再靠顏色分辨不同分類/標籤。危險色（用於刪除等破壞性操作）
  不受這條收斂影響，維持現有清楚的警示色，這是既有的合理 UX 慣例，不屬於這次要收斂的「資訊性
  色彩標記」範疇。
- **按鈕視覺層級**：現有的 `.btn-primary`（實心深色填滿）目前被用在多種頻率不同的動作上。這次
  拆成兩層：真正關鍵、低頻的動作（例如發布文章、新增文章、密碼保護確認、錯誤頁的唯一動作）維持
  `.btn-primary` 實心填滿；其餘現在也用 `.btn-primary` 但實際上是頻繁操作性動作的按鈕（例如
  搜尋、新增分類、分類/標籤節點列的行內重新命名/合併確認）改用新增的一種「輕量強調」按鈕樣式
  （淺色底、深色文字/邊框，而不是實心填滿）。原本就不是 `.btn-primary` 的操作性按鈕（篩選、
  選取、更多等）維持現有的樣式基底不變，本來就已經是這個方向。
- **卡片/邊框語言維持現狀，不做陰影相關改動**：查證後確認文章卡片、相關文章卡片目前已經是無陰影
  的細邊框樣式（只有 hover 時邊框變色），本來就符合這次想要的方向，這條在實作時不需要額外改動。
  導覽抽屜、篩選面板、更多選單、標籤輸入的下拉建議清單、密碼保護彈窗這些浮動面板維持現有的陰影，
  不套用「拿掉陰影」的規則——這些是浮在內容之上的元件，陰影是傳達「這是浮動層」的合理慣例，跟
  「淡雅化」要收斂的是靜態內容卡片的視覺雜訊，兩者不是同一件事。
- **圓角、字體、深色模式**：圓角維持現有的兩層尺度不變（現有尺度已經算克制）；中文襯線標題字維持
  現有用法（只用在少數大標題）不變；這次不做深色模式，先只做亮色版本。
- **套用順序**：先把新的 token 規則套用到最近做的共用元件（導覽抽屜、篩選面板、更多選單）作為
  示範，確認規則本身站得住腳，再依序套用到文章列表、文章詳情頁、文章編輯器、分類/標籤管理頁。
  這個順序會在 `/to-tickets` 階段展開成明確的 Parent／Blocked by 關係，不是完全互不阻塞的垂直
  切分——跟前一輪響應式改動的切法邏輯一致。

## Testing Decisions

好的測試只驗證外部可觀察的行為（畫面上實際呈現的結果、使用者能看到的規則有沒有被遵守），不綁定
內部實作細節。

- **延續既有的靜態文字掃描模式**（前例：`test/NavDrawer.test.js` 等這幾輪新增的測試檔案）：
  - 驗證新增/調整的 design token 確實被定義在 `:root` 裡，且數值符合這次定案的方向。
  - 驗證樣式表裡沒有新增寫死的 hex 值繞過 token（延續既有查證方式：全文掃描 hex 色碼，確認每個
    值只出現在對應的 token 定義處，唯一預期例外是這次要修掉的那一處寫死白字——修完之後這個例外
    也應該消失）。
  - 針對「色彩使用範圍收斂」這個核心決定寫更具體的靜態掃描，鎖住「分類色點/標籤底色不再帶有色彩
    相關的 class 或行內樣式」「狀態徽記維持既有的顏色相關 class」，避免日後不小心又悄悄加回去。
  - 針對「按鈕視覺層級」寫靜態掃描，驗證這次定案要降級的幾個按鈕（搜尋、新增分類、行內重新命名/
    合併確認）確實不再是 `.btn-primary`，改用新增的輕量強調樣式；而維持關鍵動作的按鈕（發布、
    新增文章等）仍然是 `.btn-primary`。
- **不會出現需要抽出來單獨測試的純函式**：這一輪的改動幾乎全是 CSS token 調整跟 class 名稱替換，
  沒有新增涉及邏輯判斷的 JavaScript 函式，延續前幾輪「純 CSS/HTML 改動不需要純函式抽出測試」的
  判斷。
- **人工驗收**：視覺美感本身沒辦法自動化測試「好不好看」。完成後透過 `docs/preview/Preview.html`
  在瀏覽器裡實際比對新舊畫面，確認：色彩整體變淡但文字仍然清楚可讀、狀態徽記顏色清晰、分類/標籤
  不再靠顏色分辨、按鈕層級一眼看得出哪個是關鍵動作、浮動面板的陰影感覺合理、桌面與窄螢幕呈現一致。
- **`docs/preview/` 靜態預覽檔案同步維護**：延續前兩輪的既有模式，改動樣式或樣板時同步更新這份
  預覽檔案內嵌的版本。

## Out of Scope

- 深色模式（這次先只做亮色，之後有需要再另開一輪）。
- 卡片陰影的改動——查證後確認不需要，詳見 Implementation Decisions。
- 圓角尺度的調整（維持現有兩層不變）。
- 中文襯線標題字的使用範圍調整（維持現有用法不變，不擴大也不拿掉）。
- 平板或其他斷點的獨立視覺規則（延續前一輪已經定案的 768px 兩層斷點，不因為這次視覺調整而新增
  斷點）。
- 圖示（icon）系統的重新設計——前一輪響應式改動已經建立手刻 inline SVG 的做法，這次不重新檢視。
- 任何後端（`.gs` 模組）或 Supabase 端（`schema.sql`）的變更——這次是純前端視覺調整。
- 動畫、轉場效果的新增或調整（例如按鈕的 hover/active 過場效果）——這次專注在靜態的顏色與樣式
  規則，不涉及動效系統。

## Further Notes

- 這次是純前端（樣式／樣板）調整，不涉及 `schema.sql` 或任何 Supabase 端變更，延續前兩輪的慣例。
- 這次用 `uiux` 技能查了 `nextlevelbuilder/ui-ux-pro-max-skill` 資料庫，確認這個產品類型
  （Knowledge Base/Documentation）對應的建議風格是「Minimalism & Swiss Style」，方向上支持
  「靠留白/字重分層、少用色彩」這個決定；但資料庫本身的示範色票（偏冷灰藍）跟這個專案已經建立的
  暖色調性不合，這次選擇不採用資料庫的示範色票，而是在專案既有色彩基礎上做精修——這是決策過程中
  值得記錄下來的判斷,以免未來有人以為「沒有照資料庫的建議色票」是疏漏。
- 查證過程中也發現一個原本以為存在、後來確認不存在的問題：一開始以為中文 Web Font（Noto Serif/
  Sans TC）沒有正確載入，後來重新確認 `Index.html` 其實有正確的 Google Fonts `<link>`，這個
  疑慮已經排除，不需要處理。
- 完成後建議比照專案「已知問題修復紀錄」的既有格式，在 README 新增條目記錄這次的色彩 token 微調
  與按鈕層級規則，方便以後有新畫面或新元件時，能直接查到這次定案的規則該怎麼套用，而不用重新
  一輪一輪回頭讀過去的討論。
